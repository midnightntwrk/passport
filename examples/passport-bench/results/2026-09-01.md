# Sponsored-onboarding load bench — 2026-09-01

Every figure below was taken against live Midnight stagenet. One virtual user is one
operating-system process running the demo app’s own wiring: a fresh unfunded wallet, an
account-custody contract deployed, and one `add_grant` circuit called on it — a real ZK
proof and a real sponsored DUST fee, with no value moved and no `.night` name claimed.

```
node dist/bench.mjs --render results/2026-09-01.events.ndjson --out results --shape sequential:2:balancer --shape concurrent:2:balancer --shape concurrent:5:balancer --shape concurrent:10:balancer --shape concurrent:5:balancer,gateway --shape concurrent:10:balancer,gateway
```

## Where the contention was

A sponsor serves one balance at a time. Our balancer expresses that as a reservation — its
`/wallet-status` publishes `available: 0, PENDING_TRANSACTION` and the client will not even try.
The 1AM gateway expresses it as `429 A balance transaction is already pending`, which the client
treats as waitable and retries. Both are the same ceiling wearing different clothes, and this is
where a run meets it.

| Shape | `/balance-only` 200 | 429 pending | Other refusals | Unreachable | Served by the second endpoint | Users refused at the gate |
|---|---|---|---|---|---|---|
| sequential N=2, balancer | 4 | 0 | 0 | 0 | 0 | 0 |
| concurrent N=2, balancer | 2 | 1 | 1 | 0 | 0 | 0 |
| concurrent N=5, balancer | 2 | 0 | 0 | 0 | 0 | 4 |
| concurrent N=10, balancer | 2 | 3 | 3 | 0 | 0 | 6 |
| concurrent N=5, balancer→gateway | 10 | 109 | 109 | 0 | 10 | 0 |
| concurrent N=10, balancer→gateway | 20 | 943 | 242 | 0 | 14 | 0 |

## What this bench cannot tell you

- 4 user(s) ended in `failed` rather than `refused` — an error the bench could not attribute to the sponsor’s own refusal vocabulary. Those are in the run log and should be read before any of the timings above are trusted.
- A refused virtual user gives up; a real one can press the button again. Every “refused” here is therefore a first attempt that failed, not a Passport that could never be created — the refusal rate says what a burst feels like, and the service rate says what a queue would drain at. Neither is a count of people who would go home.
- Every virtual user here is a Node process running the app’s wiring, not a browser. It does not prove in-tab, it does not carry a passkey ceremony, and it does not pay the cost of a PWA’s first load. The onboarding a real user sees is this plus those.
- The bench deploys a contract and calls one circuit. A real onboarding also registers a `.night` name and takes an activation grant, and those two run through `/register-alias` and `/fund-account`, which exist on our balancer alone — no second provider, and capped in the balancer’s own configuration at 20 and 30 per rolling hour. Nothing here measured them, and for a day of Token they are the tighter constraint.
- The bench runs from one machine on one network. It measures what the SERVICES do under concurrency; it does not measure what a conference Wi-Fi network does to 200 browsers.
