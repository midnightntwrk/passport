# GRANTS-E3: the unit and enforcement point of `kernel.blockTimeLessThan`

Evidence for the scoped-grants MIP, section 5.1 (`expires_at`, unit unpinned)
and its Testing section. The question: on the node, not in the simulator,
what unit do `kernel.blockTimeLessThan` and `kernel.blockTimeGreaterThan`
compare in, where is the comparison enforced, and what does a passing
`before(t)` mean once the transaction lands in a later block.

**Verdict in one paragraph.** The unit is **seconds since the UNIX epoch**,
on the client and on the node alike. The comparison is not proven: it is a
ledger read whose Boolean result the client records in the public transcript
and the proof merely asserts. It is enforced **twice**: the client's
compact-runtime evaluates it against the **host wall clock** (whole seconds)
and aborts the build when it is false there; the node re-executes the
transcript at **mempool admission** against its own block context and
refuses the transaction on a `ReadMismatch` when the recorded result does not
hold. The node's admission-time block time runs **8.2 to 10.2 seconds ahead of
the wall clock** on the localnet (6 s blocks), on the assumption of the 1.7 to
1.8 s build-to-submit latency measured on the refused rows: `before(now + 10)`
is refused, `before(now + 12)` is admitted and included. Measured against the
head block timestamp rather than the wall clock, the same value runs 10.0 to
14.0 s ahead; which of the two it is anchored on is not determined here. The never-expires arm
`t == 0 || blockTimeLessThan(t)` behaves on the node exactly as in the
simulator: `0` always passes and records no time read at all.

The probe contract has a `Counter passes` and three exported circuits:

```compact
export circuit before(t: Uint<64>): [] { assert(kernel.blockTimeLessThan(disclose(t)), "not before"); passes.increment(1); }
export circuit after(t: Uint<64>): []  { assert(kernel.blockTimeGreaterThan(disclose(t)), "not after"); passes.increment(1); }
export circuit never(t: Uint<64>): []  { assert(disclose(t) == (0 as Uint<64>) || kernel.blockTimeLessThan(disclose(t)), "expired"); passes.increment(1); }
```

The `disclose()` is forced by the compiler for a circuit parameter ("ledger
operation might disclose the lower bound of the time being checked"); the
MIP's `expires_at` is a ledger cell and needs none. The comparison shape is
the MIP's.

For every row the suite records the argument, the host clock at submission
(`now_s`, `now_ms`), the client's assumed time, the node head (height and the
Substrate timestamp inherent decoded from `chain_getBlock`) and the indexer's
latest block, the client phase reached (build, prove, balance, submit,
submitted), the node outcome (included with status, block height and
timestamp, or refused), and the `passes` counter before and after. Every
transaction the client submitted was included; nothing was dismissed after a
validity window, because the node refuses a failing comparison at admission.

## Conclusions

1. **Unit: seconds.** The node-side determination rests on the rows that
   actually reached the node. `before(now_s + 3600)` included (row 1) forces
   the node's value below `now_s + 3600`, which excludes a millisecond value
   (about 1.79 × 10¹²); `after(now_s - 3600)` included (row 8) forces it above
   `now_s - 3600`, which excludes both a block height (about 10³) and a slot
   number (about 3 × 10⁸). Those two rows alone bracket the node's value to
   (now_s - 3600, now_s + 3600), and the sweep narrows it to about now_s + 9.
   `before(now_ms - 3600000)` is also included on the node (row 4), which can
   only hold when the compared value is a seconds value. `before(2^63)` is
   included (row 6): the operand is a plain `Uint<64>` compared with `lt`, no
   narrower range applies. The build-time aborts agree but add no node-side
   evidence, because the node never saw those transactions: `after(now_ms -
   3600000)` (row 10) and `before(block height + 1000)` (row 7) are
   client-only evidence that compact-runtime compares against a seconds
   wall-clock value rather than against milliseconds or a height. The block
   timestamp itself is carried in milliseconds by the Substrate timestamp
   inherent and by the indexer's `block { timestamp }` (`Int`), while the
   ledger's block context is declared in seconds
   (`BlockContext.secondsSinceEpoch`); whether the millisecond value is
   truncated or rounded when the block context is filled was not measured, and
   at 1 s resolution over 6 s blocks nothing in these runs separates the two.

2. **Where it is enforced: both sides, neither of them the proof.**
   - *Client, at build time, against the host wall clock.* compact-runtime's
     `createCallContext` sets `secondsSinceEpoch = Math.floor(Date.now() /
     1000)` unless a time is passed, and neither compact-js nor midnight-js
     passes one. A false comparison aborts circuit execution with `failed
     assert: <message>` before anything is proven or submitted (rows 2, 5,
     7, 9, 10, 11, 15, 21). No block timestamp is consulted. Every one of
     those rows is client-only evidence: nothing was submitted, so they say
     nothing about the node.
   - *Node, at mempool admission, against its block context.* The recorded
     `popeq` result is re-derived by the node's VM in verifying mode; when it
     differs, the node logs `Rejected transaction <hash> from mempool:
     guaranteed execution would fail: Transcript(Execution(ReadMismatch {
     expected: <[01]: b1>, actual: <[-]: b1> }))` and answers the RPC with
     `1010: Invalid Transaction: Custom error: 104` (rows 16 to 20, extract
     rows S1 and S2, sweep rows 1 to 4 and 13). The wallet SDK wraps this as `SubmissionError:
     Transaction submission error`; the reason is only in the RPC log line and
     the node log. Nothing reaches a block and `passes` does not move.
   - *The proof constrains nothing about time.* In the ZKIR the comparison
     result is a `public_input` bound to the transcript, and `assert` fires on
     that input. The transaction is valid for whatever result the transcript
     claims; the node's re-execution is what makes the claim true on chain.
     The intent `ttl` (one hour on the contract-call intent, 60 s on the
     wallet's balancing intent here) is a separate validity window and never
     came into play.

3. **What a passing `before(t)` means.** A grantee's `before(t)` that reaches
   the chain establishes, in order: the grantee's host clock read below `t` in
   whole seconds; the node's admission-time block time, 8.2 to 10.2 s ahead
   of the wall clock on this network (10.0 to 14.0 s ahead of the head block
   timestamp, the anchor being undetermined), was below `t`; and the including
   block's time, which was below the admission-time value in every observed
   case, was below `t`. Conversely the check is *not* a statement about the
   grantee's wall clock at inclusion. Practically, an `expires_at` of `t`
   stops being usable roughly one block interval plus a tolerance before `t`
   (8.2 to 10.2 s measured against the wall clock on this localnet, and up to
   14.0 s if the node's value is anchored on the head block timestamp
   instead), and a client whose clock runs ahead refuses calls
   the chain would accept (row 21), while one whose clock runs behind builds
   calls the chain refuses (rows 18, 20).

4. **Never-expires arm on the node.** `never(0)` is included with no time
   read recorded (row 13); `never(now_s + 3600)` is included (row 14);
   `never(now_s - 3600)` aborts at build with `expired` (row 15);
   `never(now_s + 2)` and `never(now_s + 10)` are refused at admission (row
   17, sweep row 13). The arm's semantics are identical to the simulator's.

5. **Granularity and skew.** Host and node clocks agree to within the block
   production lag (host ahead of the node head by 2.3 to 3.1 s at the start of
   each run, 0 to 5 s row by row, one block being 6 s). The indexer's latest
   block lags the node head by two blocks (about 12 to 15 s), so a client that
   reads "the latest block time" from the indexer reads a value 12 to 20 s
   behind the wall clock, and 20 to 30 s behind the node's admission-time
   value. Inclusion latency from `now_s` to the including block's timestamp
   was 2 to 8 s.

## Lowering notes (full detail in .planning/grants-e3/lowering.md)

- `kernel.blockTimeLessThan(t)` compiles to an onchain VM program run through
  `__compactRuntime.queryLedgerState`: `dup 2; idx [2] (cached); push
  Cell(t: Uint<64>); lt; popeq`. Field 2 of the call context is
  `secondsSinceEpoch` (onchain-runtime `CallContext`: `ownAddress,
  comIndices, secondsSinceEpoch, secondsSinceEpochErr, parentBlockHash,
  balance, caller, lastBlockTime`). `blockTimeGreaterThan` is the same program
  with the operands swapped. `secondsSinceEpochErr` and `lastBlockTime` are not
  consulted by either.
- The generated `never` is `t === 0n || <query>`: with `t == 0` no ledger
  read happens and the transcript carries no time comparison.
- ZKIR v3 (`zkir/before.zkir`): `constrain_bits %t.0 64`, `public_input
  %t.1`, the encoded VM program as `impact` ops ending in the `popeq` with
  `%t.1`, then `assert %t.1`. In `never` the whole block is guarded by
  `%t.2 = (t != 0)` and the assert takes `cond_select(t == 0, 1, %t.3)`.
- The runtime input: `CircuitContext.time: number` ("The current time the
  circuits will assume"), fed by `createCircuitContext(..., time?: number,
  parentBlockHash?, ...)`; `createCallContext` defaults it to
  `Math.floor(Date.now() / 1000)` and writes it into
  `QueryContext.block.secondsSinceEpoch: bigint`. compact-js
  (`ContractExecutable.js`) passes `undefined`.
- Validity window: midnight-js builds the contract-call intent with
  `Intent.new(ttlOneHour())`; the wallet balances with its own ttl (60 s in
  this harness, because node 2.1.0 enforces
  `Malformed(FeeCalculation(OutsideTimeToDismiss))` for long windows). The
  chain's `global_ttl` is 14 days. `Transaction.wellFormed(ref_state,
  strictness, tblock: Date)` is the ledger entry point that takes a block
  time. The kernel comparison does not use the ttl.

## Consequences for the MIP

**Section 5.1, the unit sentence.** Replace the unpinned sentence with:

> `expires_at` is a count of whole seconds since the UNIX epoch, the unit of
> `kernel.blockTimeLessThan` on ledger 9 (recorded on-node, E3), with `0`
> meaning never. The comparison is a ledger read whose result the transaction
> records and the node re-checks at admission; it is not part of the proof.

and state the `0` arm as measured: `expires_at == 0` records no time read, so
a never-expiring grant is insensitive to block time by construction, on the
node as in the simulator.

**Section 5.1, client and authoriser obligations.** The existing "Clients
MUST sanity-check a non-zero `expires_at` against a freshly read block time
before signing" needs two corrections from the measurements:

- the client evaluates the seam against its **own wall clock**, not a block
  time, so the sanity check is against the wall clock, and a client whose
  clock runs ahead of the network refuses grants the chain still accepts
  (row 21), while one that runs behind builds calls the network refuses at
  admission (rows 18, 20);
- the node's admission-time block time runs about one block interval plus a
  tolerance **ahead** of the wall clock, so a grant is unusable from roughly
  `expires_at - (block interval + tolerance)`, 10 s on the reference
  localnet; the MIP should say that `expires_at` is a lower bound on when the
  grant stops working and that clients SHOULD treat the last two block
  intervals before `expires_at` as expired.

**Re-read-and-re-sign rule.** The grantee's failure modes are now concrete:
a build-time abort (`failed assert: expired`) when its clock is at or past
`expires_at`, and a mempool refusal (`Invalid Transaction: Custom error:
104`, `SubmissionError`) when the network's time is. Both leave state
untouched and the signed challenge valid, so the rule is: on either signal,
re-read the grant record and the chain head, and re-sign only if
`expires_at == 0` or `expires_at` exceeds the head's block time by more than
two block intervals; otherwise treat the grant as expired and request a new
one. Retrying an admission refusal without re-reading is pointless because
the network's time only advances. Clients SHOULD unwrap the RPC line (the
wallet SDK's `SubmissionError` hides the reason) and SHOULD NOT take the
indexer's latest-block timestamp as "now" (it is two blocks behind the node
here).

**Testing.** Item 1 (happy path) gains a row: `expires_at = 0` and
`expires_at = head + 3600` both execute on the node, `passes`-style state
advances, and the `0` record produces no time read in the transcript. Item 2
(rejection matrix), the "expired" fault, splits into three rows that the
suite must produce separately: (a) `expires_at` in the past, the grantee's
build aborts with `failed assert: expired`, nothing is submitted; (b)
`expires_at` within one block interval plus tolerance of the wall clock, the
build succeeds and the node refuses at admission with `Custom error: 104` /
`ReadMismatch`, state unchanged; (c) a client clock skewed behind the network
by more than the margin, same node refusal, to show the check does not rely
on the grantee's clock. A fourth control, client clock skewed ahead, shows the
client refusing a grant the chain accepts, which is a client-quality
requirement rather than a protocol property.

**Rationale note worth adding.** Because the comparison is a transcript read
rather than a circuit constraint, an `expires_at` check costs no proof
constraints beyond one public input, and no `secondsSinceEpochErr`
tolerance is applied by the ledger; the tolerance is entirely in the node's
choice of admission-time block time, which this MIP cannot pin and should
describe as network-defined.

## Caveats

- Single-authority localnet with 6 s blocks and an uncontended mempool. The
  8.2 to 10.2 s admission offset (10.0 to 14.0 s against the head block
  timestamp, the anchor undetermined) is measured here, not read from node
  source; on
  a network with a different block interval or tolerance the value differs,
  and a transaction that lingers in a full mempool past its admission-time
  evaluation was not exercised (whether the block author re-checks at block
  building is not established by these runs; the log wording "guaranteed
  execution would fail" suggests one code path serving both).
- Host and node run on the same machine, so clock skew between them is the
  block-production lag only; the ±600 s rows simulate a skewed grantee by
  shifting the one `Date.now()` compact-runtime reads.
- The probe's circuit parameters carry `disclose()`; the MIP's `expires_at`
  is a ledger cell and does not.
