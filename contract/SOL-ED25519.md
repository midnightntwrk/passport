# The `sol_ed25519` arm: a Solana wallet as a Passport device and grantee

A Passport account can be controlled by a Solana wallet: a software wallet's `signMessage` (Phantom and others), or a wallet that signs the Solana off-chain message (a Ledger or Trezor, or a software wallet's `signOffchainMessage`), each producing an RFC 8032 Ed25519 signature. The wallet needs no SOL and sends no Solana transaction. It signs one readable text per operation, in one of the two signing formats (section 3), and the contract renders that text itself from the values it executes on. The client asks each wallet only for a format it can sign, and checks every signature against the key it expects before anything is proved (section 1, "Formats by wallet").

Source: `contracts/account-sol-ed25519.compact` (included by `account.compact`), with the Ed25519 verification, key encoding and key derivation from a seed in the imported module `contracts/modules/Ed25519Core.compact`, the two signing formats in the imported module `contracts/modules/SolanaFormats.compact`, client facade `src/wallet/signer-sol-ed25519.ts`, the formats each wallet signs and the wallet adapters in `src/wallet/sol-ed25519-wallet.ts`, independent message renderer `src/wallet/sol-ed25519-message.ts`. Status of this document: the byte contract of format `sol v1` for all 16 circuits (the grammar, every layout and its length, the display inputs), the acceptance policy with the layer that enforces each rule, the formats by wallet and the signer check, the identity and its blinding per format, the restore of a blind, the network argument, recovery, the grantee role, the frozen vectors (the hardware signatures among them) and the tests, direct transfers, and privacy and provenance. Costs: [SOL-ED25519-MEASUREMENTS.md](SOL-ED25519-MEASUREMENTS.md); evidence: [evidence/sol-ed25519/](evidence/sol-ed25519/).

## 1. Acceptance policy

Each rule is listed with every layer that enforces it. "Decoding" is the honest proof server's input check: it was exercised (the evidence labels it `decoding`), but a malicious prover does not run it, so it is never counted as a constraint. "Circuit constraint" names what the proof itself enforces; where the source is a static reading of the crates the pinned proof server builds with (proof server 9.0.0-rc.8 pins midnight-zkir 3.1.0-rc.1 and midnight-circuits 7.2.4), it says so: no honest proof server lets such an input reach the circuit, so these constraints are not exercised by a prover test.

Independent oracle: Node's OpenSSL Ed25519 (cofactorless), and noble with `{ zip215: false }` plus the explicit checks above (`src/tests/sol-ed25519-offline.ts`).

**Formats by wallet.** Wallets differ in what they sign, and a wallet asked for a format it cannot sign either refuses or shows bytes its user cannot read. The client asks each wallet only for the formats it can sign (`solWalletFormats`, `src/wallet/sol-ed25519-wallet.ts`), preferred first:

| Wallet | Formats | Why |
|---|---|---|
| Phantom | raw | it signs `signMessage` bytes and refuses an off-chain message, even one the page builds; never asked for off-chain, whatever it advertises |
| Backpack, Solflare | off-chain, then raw | off-chain through their own wallet-standard `solana:signOffchainMessage` when they advertise it with message version 1 (they show the text with its line breaks), raw through `signMessage`; without the feature, raw only |
| another wallet-standard wallet | tested before enrolment: raw, else off-chain | it may advertise a format it does not honour (a `signMessage` backed by a hardware account that refuses raw bytes), so the client asks for one signature of a probe text in each format it advertises, raw first, and enrols in the first whose signature verifies (below); neither advertised, or neither verifies: it cannot enrol, and nothing is derived |
| Ledger, Trezor | off-chain | their Solana apps sign the off-chain message v1 and refuse raw bytes; never asked for raw |

Enrolment signs the blind request in the first format (section 2), a restore tries each, and a device signs its approvals in its wallet's format.

**The format probe** (another wallet-standard wallet: `probeSolWalletFormats`, `solEnrolmentSigner`). When the wallet offers `solana:signMessage`, the client asks it for one signature of a probe text in the raw format (the raw head, then the text) and checks it with the signer check, over exactly those bytes, under the account's key; if the wallet refuses, throws, or returns a signature that does not verify, and it advertises `solana:signOffchainMessage` with version 1, it asks for the same text in the off-chain format through that feature and checks it the same way. The first format that verifies is the enrolment format (a raw failure drops raw from the wallet's formats); if none does, the wallet is refused with the probe's outcome and nothing is derived. The probe text's first line, `Midnight Passport signing format check (sol v1)`, is unlike every approval's and both blind requests', so no check of the arm accepts it as either; it carries a fresh 32-byte nonce, so its bytes are new every time; its signature authorises nothing, is checked and dropped, never stored and never used as a blind. A named family is never probed. A restore without a record needs no probe: it tries the formats such a wallet advertises, raw then off-chain, and moves past a format the wallet refuses or signs wrongly (`skipped` in the result), since the blind request's own signatures are the test; with a stored record only the stored format is used. The off-chain format always goes through the wallet's own off-chain signing, never `signMessage`: handed the envelope as raw bytes, a wallet shows its binary head as garbled characters. The adapters refuse, without asking the wallet, bytes of a format it cannot sign. A Phantom account backed by a Ledger signs through the Ledger Solana app, which refuses raw bytes, so it cannot enrol through Phantom; the Ledger enrols directly, off-chain.

**The wrong signer.** With two Solana extensions installed, one may answer requests made to the other, through the other's wallet-standard entry, which reports the other's key. A key a wallet reports is therefore not evidence of who signed: the client checks every returned signature against the key it expects, over exactly the bytes the wallet was asked to sign, before anything is proved (`checkSolSignature`), and refuses a mismatch with the expected key, naming another key only when the signature verifies under it (for example another connected wallet's key, `SolSigner.others`), else saying the signer is unknown.

The client signs nothing it has not pre-checked: the wallet's signature must verify, cofactorless, over exactly the bytes of the device's format.

## 2. Identity and the blind

The device is the wallet's public key `A`, carried as a `Curve25519Point` together with the 32-byte RFC 8032 encoding the wallet exports (`y` little-endian, the low bit of `x` in bit 255) and the x-coordinate's bytes; `encode_public_key_ed25519` checks both byte inputs against the point. Entries, boot commitments and grant ids bind those 32 bytes and the account's blind:

```
blind    = SHA-256(pad32("midnight:account:blind:sol:v1") || signature(64))
entry    = SHA-256(pad32("midnight:account:device:sol:v1") || account || key || blind || le4(epoch) || le8(counter))
boot     = SHA-256(pad32("midnight:account:boot:sol:v1") || salt || key || blind)
grant id = SHA-256(pad32("midnight:account:grant:id:sol:v1") || account || key || blind || origin_hash || le1(slot))
```

The blind's signature is the wallet's signature of the readable request message of `src/wallet/blind.ts` (Midnight Passport, the network, the wallet's base58 key, the account index, and a warning that the signature reveals the account's privacy key), in a format of the wallet (`solBlindSignedMessage`):

- **raw:** the request's bytes, unchanged (`signMessage`), so a raw blind is the blind this arm has always derived;
- **off-chain:** the off-chain message v1 head naming the key (section 3), then the same bytes.

Enrolment signs it twice in the wallet's first format and refuses a wallet whose two signatures differ (`deriveSolBlind`); a grantee does the same with its own request (`deriveSolGranteeBlind`, section 7). Each signature passes the signer check. No circuit accepts a request message as an authorisation: its first line differs from every operation's.

**A device is bound to its format.** One key gives one blind per format, so a device is usable only with the blind of the format it was enrolled in; the device's identity (its key and the arm's tag) does not depend on the format. The client stores per device its arm, format, network and account index, which are not secret, and caches the blind beside them in its local storage (`solRosterEntry`: the `format` is required, the `blind` is the cache); the blind never leaves the client. A restore (`restoreSolBlind`, the shared `restoreBlind` of `src/wallet/blind.ts`) uses the cached blind as it is; else derives the blind again in the stored format and uses it only when it finds the account's entry; else, with no record, derives it in every format the wallet can sign, each tested against the account's entries (`solDeviceFinds`, at every use counter from 0 to `auth_nonce`). It never asks a wallet for a format it cannot sign, and never derives a blind in another format than the stored one. RFC 8032 derives the signature's nonce from the secret key and the message, so every wallet that follows it signs the request alike; a wallet of the same key that derives its nonce otherwise signs it with another valid signature and derives another blind, and the restore refuses that blind: "No account was found with the privacy key this wallet derives in the raw format, the format this device was enrolled through. A wallet that signs the request differently from the wallet used then derives another privacy key from the same wallet key. Use that wallet, or add this wallet as a new device from another device of the account, or through the account's recovery." (a grant: "No grant was found …, the format this grant was issued through. … Use that wallet, or ask the issuing account's owner for a new grant to this wallet.").

**Use counters.** A call presents the use counter of the device's live entry, and the client finds it on the ledger (`resolveSolEd25519Counter`, which every helper of this arm uses through `authoriseSolDeviceOn`). Every circuit that enrols a device of this arm inserts its entry at counter 0 (the activation and `add_device`), and every successful device-gated call removes the caller's entry at counter `c` and inserts it at `c + 1` in the transaction that advances `auth_nonce` by one; `auth_nonce` starts at 0 and never decreases (recovery's finalisation advances it too, and clears the device set). So an entry enrolled at counter 0 is live at a counter no greater than `auth_nonce`, and the client's scan of `0 … auth_nonce` finds it however many calls the device has made: there is no fixed ceiling. The client checks the counter it last confirmed for the account, device and epoch first (or one its caller gives: `resolveSolEd25519Counter(account, device, { counter })`, `authoriseSolDeviceOn(…, { counter })`, `SolEd25519Device.noteCounter`), then scans forward from it through that counter plus `auth_nonce` (never past 2^64 − 1, the largest counter), then from 0 up to it; the next call of a device therefore costs two membership probes. A counter a caller gives must be a `Uint<64>`, and is refused before the ledger is read otherwise. A scan runs in chunks of 256 probes and yields to the event loop between two chunks, so a long one does not block the page, and an `AbortSignal` (the `signal` option of the resolver, of `authoriseSolDeviceOn` and every helper, and of `solDeviceFinds`) stops it between chunks with an error naming the probes made and the signal's reason as its cause. An aborted resolution sends nothing and asks for no operation approval, since the call is signed only after its counter is found; a restore aborted during its scan may already have signed the blind request, because a restore derives the blind before it tests it. Upstream's `add_device_with_jubjub`, `_with_k256` and `_with_p256` take an already-derived entry, whose counter the contract cannot read: an entry derived at a counter `k > 0` is live at `k`, and the scan reaches it only while `k ≤ auth_nonce`. Above that the client refuses with the range it scanned, and the caller gives `k`.

The consequence: a device enrolled through Phantom (raw) cannot be used from a Ledger holding the same seed unless the client still holds its cached blind, since the Ledger signs only off-chain, which gives another blind. With a stored record the client names the format needed; without one, it says that no account was found in the formats this wallet can sign and that the device may have been enrolled through another format. What remains is to add the Ledger as a new device from another device of the account, or through the account's recovery: keep a second device or the recovery set up. A cached blind works from any wallet of the key, since the circuits accept both formats for every device: a device enrolled through Phantom authorises from that Ledger with off-chain approvals. A grant a wallet holds follows the same rule (`restoreSolGranteeBlind`; the remedy is a new grant from the issuing account).

`compute_public_key_ed25519(seed)`, the Ed25519 core's derivation (re-exported by the arm), derives the point from an RFC 8032 seed with the contract's own arithmetic (SHA-512, clamp, reduction mod `L`, `[s]B`), and `encode_public_key_ed25519` then checks its 32 bytes, for software signers and tests. There is no raw-scalar helper.

## 3. The signed message, format `sol v1`

### Signing formats

A wallet signs the approval text in one of two formats (`contracts/modules/SolanaFormats.compact`, client `solSignedMessage`), each a fixed 50-byte head followed by the same text:

| Format | Head (50 bytes) | Wallets |
|---|---|---|
| raw | the ASCII line `Midnight Passport, Solana signMessage format (v1)` and a line feed: `4d69646e696768742050617373706f72742c20536f6c616e61207369676e4d65737361676520666f726d617420287631290a` | `signMessage`: Phantom; Backpack and Solflare without their off-chain signing |
| off-chain message v1 | `ff` ‖ `solana offchain` (the signing domain, 16 bytes) ‖ `01` (version) ‖ `01` (signer count) ‖ the signing key's 32 bytes | Ledger and Trezor; Backpack and Solflare through `solana:signOffchainMessage` |

A wallet-standard wallet offers its features to all its accounts, while each account lists the features it supports (`WalletAccount.features`, which the standard defines as "Feature names supported by the account. This must be a subset of the names of features of the Wallet."). The client uses only the wallet's features that the connected account lists, before the rules per wallet (`solAccountFeatures`): a Solflare or Backpack account that lists only `solana:signMessage` signs raw, one that lists only `solana:signOffchainMessage` signs off-chain, and the other format is never asked. The standard makes the list part of every account, so an account object without one supports no feature the client can rely on and is asked nothing; an adapter that builds account objects itself must carry the account's `features`.

The circuit hashes R ‖ A ‖ head ‖ text once (SHA-512) and verifies once. The authorisation's flag `offchain` selects the head; it is a private input and never disclosed, so one circuit and one verifier key serve both formats and the chain does not learn which kind of wallet signed (section 11). The off-chain head's signer is the key the seam derived and checked against the point the signature is verified under, so an envelope naming another signer is not the verified message. A device is its key whatever the format: a signature made in one format verifies only in that format, and a wallet that can sign the other format with the same key authorises through the same device. The text below is the same in both formats.

### The text

```
Midnight Passport approval (sol v1)        circuit-fixed first line: the format and its version
Operation: <title>                         fixed per circuit
Site: <label>                              the site's words (32 bytes), marked as the site's
Role: device of this account               or "Role: grantee of a scoped grant"
Account: <64 hex>                          the account's contract address
Signing key: <base58, padded to 44>        the signer's Ed25519 key as Solana wallets show it
<operation lines>                          every operand and consumed witness value, in full
Consequence: <...>                         fixed, on authority-granting operations
Device nonce: <20>                         device role: auth_nonce
Grant label: <32> / Grant slot: <3> /      grantee role: the grant's identity and freshness
Grant issued at nonce: <20> / Grant use nonce: <20>
```

Rules:

- Printable ASCII and LF only; no final LF. Every line starts with text the circuit fixes.
- Numbers are decimal, left-aligned and space-padded to their type's full width (`Uint<8>` 3, `Uint<32>` 10, `Uint<64>` 20, `Uint<128>` 39), so each layout has one fixed length. The digits are display inputs that the circuit checks against the value: for each value exactly one text is valid.
- Every `Uint<128>` amount, cap and maximum coin value (`Amount (base units)`, `Spent coin value`, `Change back to this account`, `Max coin value`, `Per-call cap`, `Total cap`, `Window cap`) is shown as its base units in full, the 39 digits. A value with an exact protocol meaning gets a fixed word, selected by exact equality: a grant expiry of 0 reads `never` (`expiry_text`; other expiries stay in seconds), a zero rate-limit window reads `no window` on the `Window length` line and, when the cap is zero too, on the `Window cap` line (`window_text`, `window_cap_text`; the scoped-grants MIP reserves both fields and upstream refuses any other value today), and on `issue_grant`'s scope line an all-zero RP hash reads `not applicable` (`rp_hash_text_from_hex`).
- A grant's expiry is also shown as a UTC date and time on the next line, `Expires at (UTC): yyyy-mm-dd hh:mm:ss UTC` (Gregorian calendar, years 1970 to 9999; above 9999-12-31 23:59:59 the exact words `after 9999-12-31 23:59:59 UTC`; `never` for 0), checked against the executed seconds by the base's `expiry_datetime_text` with a checked year split.
- A Solana key (the `Signing key` line, and a Solana target or grantee) is shown as its base58 text, as Solana wallets and explorers show it: the Bitcoin alphabet, one `1` per leading zero byte, left-aligned and space-padded to 44 bytes; the base's `base58_text_32` checks the digits against the key's 32 bytes (the same checked bytes the derivations bind) with three read-back hints. Every RP hash shown has an effect: a passkey target's descriptor line shows the target's own hash in hex, never zero (`add_device` and `remove_device` by descriptor refuse a zero one through the target's derivation), and on `issue_grant` the hash is non-zero exactly when the grantee is a passkey and the scope can spend — upstream checks a grant's RP pin only on the passkey spend path — so a spending grant to a passkey shows its hash and every other grant, a read-only grant to a passkey included, carries zero and reads `not applicable`. A passkey entry with a zero RP hash that an upstream arm planted (their raw `add_device` takes any entry) cannot be removed by descriptor, since the derivation refuses the zero hash; it is removed with the literal form ("Removes a device this wallet cannot identify"). The client's copies of these texts are the base's `src/wallet/rendering.ts`.
- Bytes are lowercase hex, two digits per byte, in full. Curve coordinates and Field values are shown in the one order every arm and the base's comparison display use (`COORDINATE_DISPLAY_ORDER` in `src/wallet/descriptors.ts`): secp256k1 and P-256 coordinates big-endian, as SEC1 and their wallets show them; JubJub coordinates little-endian, Midnight's own encoding and the bytes the entries bind; Field values (the recovery session's backup vector) little-endian.
- The site chooses two texts, and the circuit marks both as the site's: the label after `Site: ` (visible words separated by single spaces), and, on a moved amount, the decimal point and symbol after `This site labels it: ` (0 to 18 decimals, a symbol of 1 to 8 visible characters whose first is a letter, so the symbol never reads as more digits of the number, as in `1 000`; the digits are the amount's). Neither can contain a line break, so neither can start a line, and neither moves value.
- Enumerated values are shown as circuit-fixed words, each selected by the value and refused for any other value: the recipient kind (`any recipient`, `unshielded user address`, `shielded coin public key`, `contract address`) and a `k256` key's signing envelope (`SHA-256 of the challenge`, `dApp-connector signData`), both from the base's rendering module (`recipient_kind_text`, `k256_envelope_text`, the same texts as the EVM arm's and the client's `labels.ts`), and the operation flags and the caller restriction (`yes`, `no`). A grant to `any recipient` carries no recipient: `issue_grant` refuses a non-zero one, so the `Recipient` line never shows a value that nothing enforces.
- No digest, fingerprint or truncation. The only hash-like values ever shown are these four, each under its fixed label: a `k256`/`jubjub` grantee's origin hash (`Grantee site label (hash)`), a passkey's RP hash (`Passkey RP (hash)`), a target's or a grantee's blind (`Device privacy salt`, `Grantee privacy salt`: a grantee's blind comes from its own request naming the issuing account, never from a device request), and the literal entry of a revocation-only removal (`Removes a device this wallet cannot identify` / `Device entry`).
- Another key (`add_device`, `remove_device`, `issue_grant`, `revoke_grant`) is a readable descriptor: its registered tag as text, then its key: an EVM address and a passkey origin in the form their own wallets show; a Solana key as its base58 text (as above); `k256`, `jubjub` and passkey keys as coordinates in the order above. Every kind renders into one fixed-length block (padded with spaces before its last line break), and the circuit derives the entry or grant id from exactly those values; a field the kind's class does not use must be zero, so two targets never render the same bytes. The kinds are listed once, in the contract's `sol_kinds()` and the client's `SOL_KINDS`, in the same order: each kind's device and grant-id tags, the class of its key (which fixes the fields it uses and its derivation) and its key lines as a device and as a grantee. A kind of an existing class is added as one entry in each, its two rows of key lines and its tests. **Additive in source, not in keys:** a new kind, or a new readable arm registered in the shared registry, is new entries and new files, but it changes the ZKIR and verifier keys of the readable arms' enrolment and grant circuits (their key blocks and tag lists grow). A deployed account has retired its maintenance authority and cannot take new keys, so such an upgrade is new code, new keys and a new account version.

### Display inputs

Compact has no division, and turning bytes into characters costs about 140 rows per byte in-circuit, so the caller supplies every text the circuit cannot cheaply derive, and the circuit **checks** each against the value it describes:

- decimal digits (left-aligned, space-padded): read back to the value;
- the site's amount label: its digits read back to the amount;
- base58: each Solana key's base58 digits (58 marks a padding position) and three read-back hints, checked against the key's 32 bytes by the base's `base58_text_32` (canonical: every digit below 58, padding only after the last character, exactly one `1` per leading zero byte);
- a date: the expiry's UTC text and its year split, checked against the seconds by the base's `expiry_datetime_text`;
- hex: two arguments per message. `frame` holds the account's nibbles and the signing key's base58 inputs: the seam checks them against `kernel.self()` and the key bytes it checked against the point the signature is verified under. `hex` holds the nibbles of every other value the message shows in hex. Both are high nibble first, each value in its stored byte order (curve coordinates little-endian, Field values as their canonical 32-byte little-endian encoding); the circuit assembles the bytes from them, asserts they equal the value, and makes each digit with one comparison;
- characters of the site label, a grant label and a passkey origin: assembled and compared with the bytes (the site label is only text; its shape is checked).

The seam (`require_authorised_with_sol_ed25519`) renders the common frame itself: the first line, the account (`kernel.self()`), the signing key in base58 (the key bytes checked against the point the signature is verified under), and the freshness tail (`auth_nonce`, or the grant's label, slot, issue nonce and use nonce). A gated circuit passes it only its circuit-fixed title and the body it renders from its operands, so no circuit can pass an identity, an account, a nonce or a frame of its own.

For each value exactly one input is valid, so the inputs add no freedom; a literal removal, which shows no target, must carry the display inputs of an empty target. `src/wallet/sol-ed25519-message.ts` builds all of them (`solShow`, `solAmountShow`, `solFrameNibbles`, `solTargetShow`, `solScopeShow`, `nibblesOf(...solDeviceHexValues(...))`, …).

### Never a Solana transaction or off-chain message

A raw `signMessage` signs whatever bytes it is given, so what it signs must never read as anything else. Every raw message (the raw head, then the text) and every raw blind request (section 2, unchanged texts) starts with `Midn` (bytes 77, 105, 100, 110).

- As a legacy transaction message, that is a header (77, 105, 100) followed by a key count of 110, so a parse needs at least 3 + 1 + 110 × 32 + 32 + 1 = **3,557 bytes**. The longest raw message is 50 + 1,690 = 1,740 bytes, and the longest raw blind request (a 32-character network name, the largest account index, a 44-character key, or a grantee request's issuing account) is shorter still. The bound is tight: an independent parser of the wire format accepts a `Midn` buffer of exactly 3,557 bytes and refuses one of 3,556 (`src/tests/sol-ed25519-message-offline.ts`, which runs the parser on every raw message of the corpus and on the raw blind requests at their longest).
- Even at that length, such a message never passes Solana's sanitize rules: its header claims 105 read-only signed accounts out of 77 required signatures, so there is no writable fee payer.
- The first byte is below `0x80`, so it is not a versioned message, and it is not `0xff`, so it is not the off-chain message envelope (`0xff "solana offchain"`).
- As a signed transaction it would carry 77 signatures (4,928 bytes).
- No message contains the Sign-In With Solana statement.

An off-chain message is the Solana off-chain message envelope by design, which wallets sign only as an off-chain message: it starts with the signing domain `0xff "solana offchain"`, which parses as no Solana message (the first byte would make it a versioned message of version 127, which does not exist) and as no transaction (the first two bytes would count 14,847 signatures, far beyond its at most 1,740 bytes). The independent parser reads every off-chain message of the corpus as an off-chain message v1 with one signer, the signing key, and the text as its message, and as no transaction or message.

An off-chain blind request has the same head (section 2), so it is an off-chain message v1 too; its text is a blind request (`assertSolBlindRequest`), never an approval text. `assertSafeSolMessage` (raw) and `assertSolOffchainMessage` (off-chain), and `solBlindSignedMessage` for the blind requests, check every signed message before any wallet is asked. The frozen corpus (`src/tests/vectors/sol-ed25519-messages-v1.json`) holds the contract's circuits and the independent renderer to each other byte for byte; its texts are the same in both formats.

## 4. What a person can check by eye

- **Comparable with what the other wallet shows**: an EVM address (`0x` and 40 lowercase hex digits; the wallet shows the same digits, mixed-case by EIP-55), a passkey origin (its exact text), the amounts in base units and the site's labels as text.
- **Comparable with what Solana wallets show**: every Solana key, in base58 (the `Signing key` line is the signer's own address as Phantom shows it; a Solana target or grantee is its address).
- **Readable without a tool**: a grant's expiry as a UTC date and time beside its seconds; a zero window as `no window`; the words for exact protocol values (`never`, `not applicable`). No wallet shows these; they are readable forms of the values the circuit executes.
- **Shown in full, but not comparable by eye with the wallet**: `k256`, `jubjub` and passkey keys (coordinates); the account address; tokens, nonces and ciphertexts. For a new device or a grantee of those classes, the check is the comparison display: the new device's own client renders the identical descriptor (`describeDescriptor` in `src/wallet/descriptors.ts`), and the user compares the two screens.

A Solana target of `add_device`, `remove_device`, `issue_grant` and `revoke_grant` (another device or a grantee) is also carried as a `Curve25519Point`, as the signing device is: the gated circuits take it beside the descriptor with its 32 bytes and x bytes (`target_pk`, `grantee_pk`; every other class passes the identity and zero bytes) and require the 32 bytes the message shows and the entry or grant id binds to equal the point's encoding, checked in-circuit by the same function the seam uses, which refuses the identity (`A ≠ O`); the point type admits only the prime-order subgroup (section 1). So a target can only ever be a usable key, and the key a user enrols is the key that later signs. The client decodes the wallet's 32 bytes strictly first (`parseSolanaPublicKey`). (The key is a separate, internal struct argument because compactc 0.35.0 aborts on a `Curve25519Point` field in an exported struct.)

## 5. Networks

An approval names no network: no `sol v1` layout carries a network value, and the contract holds none. It binds the account address (`Account:`), the role and operation, the operands, the signer's key and the freshness state (`auth_nonce`, or the grant's nonce). An account can be cloned onto another network at the same address, and an approval for it would then authorise the same call there, if the clone reached the same `auth_nonce` with the same device entry. No in-contract value could tell the clone apart: a sealed value is copied with the clone, and circuits cannot read the network id. Clients make the case unlikely by deploying with random nonces (the address depends on them), and the residual is the ledger's: binding the network id, which the upstream ledger issue proposes. The [arm's specification](../docs/mps-mip/mips/mip-xxxx-sol-ed25519-arm.md) gives the full argument. The network named in the blind request (section 2) is a client convention that gives each network its own blind; no circuit checks it, so it does not bind an approval to a network.

## 6. Recovery (the recovery MIP, sections 5 and 6)

`publish_recovery_session_with_sol_ed25519` and `recover_cancel_with_sol_ed25519` pass the device seam (over `auth_nonce`, section 3) and then call the shared chips unchanged: `do_publish_recovery_session` (no recovery pending; a vector of 1 to 4 values with the unused slots zero; a fresh, non-zero session identifier; a fresh recovery key that is not the identity and has no small order) and `do_recover_cancel` (something pending). The recovery gate itself, `recover_submit` and `recover_finalise`, is upstream's and does not depend on the arm.

The session's approval shows every operand in full under the consequence line `Consequence: sets this account's recovery key; its holder can take over this account after the veto window.`: the new recovery key's two JubJub coordinates and the four backup vector values as 64 hex digits each, little-endian (section 3), the session identifier, the vector length in decimal, and the 64-byte key wrap in two lines (1,230 bytes). The cancel shows the frame and `Consequence: the pending recovery of this account is cancelled.` (371 bytes). Each `Field` has exactly one rendering (section 1, the last row).

Finalisation clears every device entry (upstream #183), so after a recovery every old `sol_ed25519` device is refused by membership, including an entry an upstream arm's raw `add_device` planted at `device_epoch + 1` before the recovery: without the clear, that plant would be live at the new epoch. This arm's own `add_device` enrols only at the current epoch and counter 0 (section 3). The successor, a JubJub device, enrols new devices, and a fresh `sol_ed25519` device can then publish a new session.

## 7. The grantee role (the scoped-grants MIP)

A Solana key can also hold a scoped grant on an account. `issue_grant_with_sol_ed25519` shows the grantee's readable descriptor (for a Solana grantee: the 32-byte key, its grantee privacy salt and the site label the issuer chose) and every scope field; the circuit derives the grant id from exactly those values with the grantee scheme's own grant-id recipe. The grantee then signs its own messages ("Role: grantee of a scoped grant") through `withdraw_unshielded_with_grant_sol_ed25519`, `withdraw_shielded_with_grant_sol_ed25519` and `withdraw_shielded_to_contract_with_grant_sol_ed25519`. They show the grant's label, slot, issue nonce and use nonce, never `auth_nonce`, and no grant call reads or advances `auth_nonce` or a device entry.

- **Wallet-key grantees.** A grantee key is a wallet key reused across sites, not a key bound to one origin. Its `Grant label` is a label the issuer chose and the grantee's wallet shows; it is not an authenticated origin (the origin hash is SHA-256 of that label). The compensation is readable per-call consent: every grantee call shows its amount (in full digits), its recipient, the spent coin and the grant's identity.
- **The grantee's blind** is not its device blind. The issuer must know it to derive the grant id, so it comes from the grantee's own request (`granteeBlindMessage`: "Midnight Passport grantee privacy key", the role, the network, the wallet and the issuing account's address). An issuer therefore never learns a device blind, and each issuer gets its own.
- **The grant's scope salt is derived, not chosen.** `issue_grant_with_sol_ed25519` takes no salt argument. It computes `SHA-256(pad32("midnight:account:salt:sol:v1") || blind || account || auth_nonce)` with the base's `derive_grant_scope_salt`, where `blind` is the issuing device's blind (bound by the device entry the seam checks) and `auth_nonce` is the value the device signed. The shared chip hashes it into the grant's object, spent, RP and caller commitments. So whoever builds the proof cannot make those commitments public with a known salt, cannot link two grants by reusing one, and cannot leave the grantee without the one it needs; each issuance gets its own. The client's `issueGrantWithSolEd25519` returns the same value (`solGrantScopeSalt`), for the issuer to hand to the grantee off chain; the grantee opens the commitments with it when it spends. Upstream's arms instead bind a salt the caller chooses in the signed challenge (`scope_digest`); this arm's messages carry no digest, and a salt the wallet showed could not be judged by eye.
- **A fresh read key per account and grant.** The ledger stores a grant's read key only as `read_pk_hash`, in the clear, so a reused read key would link grants across accounts. The grantee's client derives it per grant: `solGranteeReadKey(secret, grantId)` (`SolEd25519Grantee.readKey(secret, account, slot)`), an X25519 pair whose secret is the clamped SHA-256 of `midnight:account:grant:read:sol:v1`, a 32-byte secret the grantee keeps and the grant id.

Upstream's shared chips run unchanged inside the arm's circuits. They are covered by upstream's own suites and by upstream's suites run on this branch (the last row above). The arm's wiring into them, which values it passes and where, is covered by the arm's own cases on those values (scope operations, caps, pins, caller, openings, the removal guards) and by mutation runs of those calls. The chip asserts concerned, which this suite refuses at the runtime layer only or not at all:

- `do_issue_grant`: `grant already active`, `empty scope`, `read-only grant cannot restrict caller`, `shielded spend requires read`, `per-call cap above cap`, `spend without cap`, `coin bound below per-call cap`, `read without delegate key`, `window bounds reserved`, `read-only grant carries object fields`;
- `do_revoke_grant`: `unknown grant`, `grant not live`;
- `do_add_device`: `device entry already present`.

The suite does refuse at the constraint level, as part of the arm's cases, the asserts of `do_remove_device` (`cannot remove last device`, `cannot remove the authorising device`, `unknown device entry`), of the grant spend (`check_spend_scope`, `check_shielded_grant_bounds`: the operation, the caller pin, the scope object, the per-call and cumulative caps, the spent opening, the recipient pin, the coin bound, the encryption key) and of the recovery chips (`do_publish_recovery_session`, `do_recover_cancel`).

The constraint-level run of record (the registered build) and the on-node runs are recorded in [evidence/sol-ed25519/](evidence/sol-ed25519/).

## 9. Measurements

All 16 circuits are at k ≤ 18 (see [SOL-ED25519-MEASUREMENTS.md](SOL-ED25519-MEASUREMENTS.md) for k, rows, message lengths, key sizes and proving times). The signing format's 50-byte head adds a SHA-512 block where the text ends within 50 bytes of a block boundary; the widest circuit is `issue_grant_with_sol_ed25519`, whose 1,740-byte signed message hashes in 15 SHA-512 blocks. Every raw message is below the Solana parse bound (section 3), and the 68-circuit roster deploys in waves of at most 15,000 verifier bytes.

## 10. Direct transfers (MIP-0012 §6.6)

`withdraw_shielded_to_contract_with_sol_ed25519` and its grantee twin send a shielded coin to another contract, which must claim it in the same transaction with its own `deposit_shielded`.

- midnight-js 5.0.0-rc.2 refuses to build the sender's call alone (`assertReceivesMatchClaims`). The arm's node tests build it with a test-only copy of the builder without that pre-check; the node still checks the claim.
- The ledger matches a claimed output to its receive by segment, commitment and recipient: both calls go into one intent, with the recipient's call moved into the fallible segment when the sender's claim is partitioned fallible.

**The effect of a failed fallible half.** The seam's state change (the device entry rolled, `auth_nonce` advanced) and the transfer can sit in different segments. If the transfer's fallible segment fails, the guaranteed segment still applies: the approval is consumed, the fees are paid, and no coin moves. The device signs a fresh approval to try again; a client presents the failure as "not sent; approve again", never as pending.

## 11. Privacy and provenance

**What the blinding gives.** The ledger holds, for each `sol_ed25519` device or grantee, only SHA-256 outputs over its 32-byte key and its blind: the boot commitment, the entries and the grant ids. Without the blind a known Solana address cannot be tested against them. The point, the key, the blind, the signature and the message are private inputs of every proof; a review of every `disclose` in the arm finds no other path, and a needle scan of every transaction and contract state of the arm's localnet runs found none of them in the clear (key, reversed, hex and base58 text, point coordinates and limb forms, every device and grantee blind), and no entry or grant id under a zero or missing blind ([evidence/sol-ed25519/privacy-review.json](evidence/sol-ed25519/privacy-review.json): the review at the current contracts; the scan over every block of the arm's localnet runs, the current build's included).

**The signing format.** The authorisation's flag `offchain` (section 3) is a private input of every proof and is never disclosed: no `disclose` reaches it, the compiler refuses every undisclosed path from such a flag to the ledger (the compiled controls of `npm run check:sol-ed25519-taint-controls`), a taint analysis of the compiled ZKIR of every circuit of the arm finds it in no public instruction (`src/tests/sol-ed25519-taint-offline.ts`, an analysis of the compiler's output that complements the functional tests), and one operation from the same state, with the same key, blind, counters and public operands, leaves equal public transcripts in both formats (`sol-ed25519-seam-offline` group 6; at the proof server, `npm run test:sol-ed25519 formats`). The claim is about what the chain shows: the signing wallet, and whoever proves the call with its private inputs, see the format.

**What it does not give.** Whoever obtains the blind request's signature (a phishing page showing the request) learns the blind and can recognise the account's entries: a loss of privacy, not of control, since the blind authorises nothing. The client's cached blind is the same secret: it stays in the client's local storage, is never sent, and is protected as the wallet's session data. A non-deterministic signer cannot re-derive its blind; enrolment signs twice and refuses it.

**Auto-approve.** A wallet setting that signs messages without showing them (for example a time-limited "auto-approve message signing") signs Passport approvals unseen as well. Passport cannot detect it; such a setting must stay off for a wallet that holds a Passport device or grant.

**What every call makes public.** Which arm and role it uses (its circuit name); blinded device entries and grant ids; the grant's salted commitments; on a shielded spend, the change bit; and what upstream's shared chips publish by design: unshielded amounts, recipients and balances, the inbox ciphertexts and the encryption key, the scope fields upstream stores in the clear (the operation flags, `read`, the caps, the expiry and the window), `read_pk_hash`, the recovery material, and the counters (`auth_nonce`, the device epoch, the grant generation, the round).

**Inherited exposures** (upstream's design or the standard library's, stated here, not changed by the arm):
- a permissionless deposit changes the shared `round` that every gated call reads, so a call prepared before it must be proved again (its approval stays valid; no funds are at risk);
- `sendShielded` derives its output nonces from the spent coin's nonce, so whoever knows a spent coin (its depositor, say) can find the spend, recover its amounts and test its recipients;
- a hosted or delegated proof server sees the key, the blind, the signature and the signing format of every call it proves, so it learns which wallet holds the account; the client should prove locally;
- a read key reused across grants links them through `read_pk_hash` (the client derives a fresh one per account and grant, section 7);
- one device's rolling entries form a public chain of its activity within the account (each call replaces its entry with its successor);
- `jubjub`, `k256` and passkey devices and grantees enrolled through this arm use upstream's unblinded recipes, so whoever knows such a key can test it against the account;
- a to-contract spend may name the account itself: no coin is stranded, but no inbox entry is written and a grantee's cap is consumed.

**Provenance.** The wallet shows every key and every piece of recovery material in full, but showing a key does not prove whose it is. Approving `add_device`, `issue_grant` or `publish_recovery_session` with a key or recovery material supplied by an attacker gives the attacker what the circuit-fixed consequence line says ("gives this device FULL control of this account", "lets the grantee key below spend from this account within these limits", "sets this account's recovery key; its holder can take over this account after the veto window"). The mitigations: the consequence lines are circuit constants; the new device's own client renders the identical descriptor for comparison (MIP-0013 S7; it shows a Solana key in base58, as the message and the wallet do, and in hex); recovery material comes from the client's own guardian ceremony. What remains is documented, not closed: a key the user cannot check by eye is trusted on the strength of the client that shows it.

## 12. Migration from the earlier draft of this arm

The arm keeps its name, `sol_ed25519`, and its 16 circuits keep theirs. Every change below is breaking, and there are no compatibility aliases.

**The signed bytes.** An approval was the text alone, signed with `signMessage`. It is now a 50-byte head followed by the same text (section 3): raw, the line `Midnight Passport, Solana signMessage format (v1)` and a line feed, or the off-chain message v1 head naming the signing key, which a hardware wallet and the off-chain feature of Backpack and Solflare sign. The texts are unchanged (the 69 frozen messages are equal), but every raw approval's bytes changed: a signature made for the earlier arm does not verify under this one, and a wallet signs again. The blind requests did not change in the raw format, so a raw blind, and with it every device entry, boot commitment and grant id derived from it, is the one the earlier arm derived; the off-chain format is new, and gives another blind (section 2).

**The circuits and the keys.** 15 of the 16 circuits have a new ZKIR and new keys: `add_device`, `append_inbox`, `issue_grant`, `publish_recovery_session`, `recover_cancel`, `remove_device`, `revoke_all_grants`, `revoke_grant`, `rotate_enc_key`, `withdraw_shielded`, `withdraw_shielded_to_contract`, `withdraw_shielded_to_contract_with_grant`, `withdraw_shielded_with_grant`, `withdraw_unshielded` and `withdraw_unshielded_with_grant` (each `…_with_sol_ed25519`, or `…_with_grant_sol_ed25519`); `activate_initial_device_with_sol_ed25519` keeps its keys, and so do the account's other 52 circuits. Each verifying circuit's authorisation gained the private flag `offchain` that selects the head. An account deployed with the earlier circuits keeps their verifier keys, and the wave deploy retires the maintenance authority, so such an account cannot take the new keys: its owner moves to an account deployed with these circuits.
