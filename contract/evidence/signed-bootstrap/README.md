# Signed-bootstrap implementation evidence — Passport #213

This directory records validation of the schema-4 reference implementation of the [temporary JubJub bootstrap amendment](../../../docs/mps-mip/mips/mip-0013-temporary-jubjub-bootstrap-amendment.md), including its B01–B13 evidence requirements. The implementation is at `c24b1e9`; `9e14998` changes the on-node funding fixture to a faucet-issued, non-native asset. Source and generated-artifact hashes identify the exact code used by each capture.

**On-node result: PASS.** [signed-bootstrap-conformance.json](signed-bootstrap-conformance.json) records 10 successful transactions and 9 timed account proofs. The run resumes a persisted deployment checkpoint, creates the software passkey afterward, activates from retained approval after erasing the temporary key, preserves an intervening deposit and pending recovery, vetoes recovery, rotates the viewing key, withdraws funds under both device arms, and adds/removes a device. All 53 installed verifiers and maintenance-authority retirement are checked. This is a software-authenticator flow; it is not a physical browser ceremony.

The native check's 36 rows include positive controls. The 17 constraint-stage rows are not 17 independently rejected attacks. The full valid activation satisfies the pinned backend's `MockProver`; unchecked `s + r_J` and `r_J` fail for the full compiled activation. The response-range subgraph also accepts its legitimate endpoints and rejects oversized responses. Coordinate-bound JubJub projections exercise order-two, mixed-torsion, and altered-coordinate assignments. Identity succeeds in the projection because point assignment alone does not impose the activation's explicit nonidentity requirement. The full activation's preprocessing rejects identity. The two off-curve projection attempts panic during unchecked host arithmetic; they do **not** establish constraint rejection.

[constraints.json](constraints.json) pins the backend revision and runner/test/source hashes. Its `runtimeEvidenceSha256` refers to the preserved [native-runtime-preimage.json](native-runtime-preimage.json), which matches that run. [runtime-preimage.json](runtime-preimage.json) may be regenerated by subsequent runtime tests and should not be substituted for that snapshot. The native scope does not include arbitrary advice-cell corruption, unchecked internal P-256 witnesses, or all possible noncanonical SHA challenge witnesses. MockProver satisfaction/rejection is distinct from cryptographic proof generation and ledger admission.

For `activate_initial_passkey`, the measured circuit has **`k = 18` and 193,751 rows**. Its prover artifact is **495,229,501 bytes** and verifier artifact is **2,889 bytes**. [circuit-sizes.json](circuit-sizes.json) records the complete roster, sizes, hashes, verified manifest, compiler 0.35.0, runtime 0.20.0, ZKIR version, and measurement host. [keygen.json](keygen.json) records **1,290.727 seconds (21 minutes 30.7 seconds)** for generating keys for all 53 account circuits. That is whole-build key-generation time, not activation proving time. The activation proof took **29.320 seconds** and was **6,460 bytes** in the successful run. This is one observation, including provider key lookup/loading and local HTTP transfer, excluding signing, wallet balancing and inclusion; it is not a cold-cache benchmark or statistical estimate. Other per-circuit durations are in the node receipt/journal. [environment.json](environment.json) records tool-binary and container-image identities and host/Docker resources.

The first node attempt did not complete: the Night deposit was rejected with `OutsideTimeToDismiss`. [night-deposit-refusal.json](night-deposit-refusal.json), [its captured output](night-deposit-refusal.txt), and the [node refusal excerpt](night-deposit-node-refusal.txt) preserve that failure. It occurred in funding and is not evidence that bootstrap authorization failed. The second attempt uses the existing faucet fixture's non-native asset; [on-node.txt](on-node.txt) and the timestamped `on-node-*.jsonl` journals retain its successful result and the earlier attempt. The second run leaves 800 of its 1,000 non-native test units after two authorized withdrawals; ledger limits were unchanged.

The temporary key authorizes only initial installation; it is not a recovery key or a device spending key. A separately retained birth recovery secret remains an independent authority. The reference's default discarded birth secret does not establish usable recovery, and a stored recovery wrap is not proof of decryptability. The full verifier roster and maintenance posture must be checked before approval: an active maintenance authority can replace verification logic. These trust assumptions and the bounded evidence above remain relevant even after a successful on-node run.
