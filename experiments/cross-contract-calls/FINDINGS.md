# Findings: cross-contract calls on the ledger-9 toolchain

**Date:** 2026/09/03 (P0 to P7); extended 2026/09/14 (P8, P9)
**Question:** how do Compact cross-contract calls work end to end on the
current toolchain, and can the passport account contract participate?
**Answer:** they work on the released stable pin set today, failure is atomic
on-node, the account contract composes as a callee behind its authorisation
seam unchanged, and value moves: unshielded and shielded tokens cross the
call boundary atomically, send paired with a same-transaction claim. The
ledger's per-frame caller derivation, run with the ledger's own code on our
transaction bytes, names the calling contract for every sub-call (P8), and a
contract can lend that identity to a root call it never made by emitting a
chosen-argument claim, which the node admits (P9).

## What the evidence establishes

### 1. In-circuit cross-contract calls are live on the released stack (P3, headline)

`caller.write_then_read(42)` cleared a fresh localnet as one transaction:
the proof server proved the call tree in under a third of a second, the node finalised it
(`SucceedEntirely`), and both ledgers moved together (`tally.total` 0 to 42,
`caller.last_observed` to 42). Nothing branch-only was needed: compactc
0.34.0 stable, compact-runtime 0.19.0, midnight-js 5.0.0-beta.7, and the
published localnet images suffice. The client-composed two-contract graft
validated on 2026/07/16 now has a contractual successor: composition is
expressed in the circuit, not assembled by the client.

### 2. One proof per source-level call, not per callee contract (P0, P1, P3)

The runtime records one `callProofDataTrace` entry, and hence one
`ContractCallPrototype` and one proof, per source-level call.
`write_then_read` (one `set`, one `get`) produces a three-entry trace and a
live transaction carrying three contract calls. Sub-call entries carry the
communication commitment; the root does not. Proof count, transaction size,
and observer surface therefore scale with the number of calls written in the
circuit, not with the number of counterparty contracts. The keyed compile
(P0) shows where the static cost lands: each cross-contract circuit in the
caller carries a prover key of roughly 280 KB against 22 to 75 KB for the
leaf circuits, and its bundle embeds an `expectedVk` fingerprint for every
callee circuit it calls, which is the implementation-binding guard real keys
make checkable.

### 3. The indexer resolves callee state (P2)

The upstream-flagged weak link is absent: indexer-standalone 4.4.0-rc.2
answers the block-pinned `contract(address:, offset:)` GraphQL query the
callee-state resolver issues, and a contract-typed constructor argument
(`{ bytes: encodeContractAddress(address) }`) round-trips through deploy and
the ledger intact.

### 4. Failure is atomic on-node (P4)

A composed `compose_guarded` transaction, proven against pre-interleave
state and invalidated by a direct `tally.set` before submission, was refused
at the submission RPC; a matched-delay control (built, proven, held the same
time, submitted unchanged) landed, so the refusal is the staleness, not TTL.
Neither contract's state moved from the stale transaction. This confirms the
documented all-or-nothing model on a released stack for the first time. The
one blemish is diagnostic, not semantic: the wallet SDK wraps the node's
refusal as a bare `SubmissionError` with no ledger error code attached.

### 5. The account contract is a viable callee, seam intact (P5)

The k1-arm account contract (vendored at commit `2b0b55d`, recompiled with
keys under ZKIR v3) accepted an owner-authorised `rotate_enc_key_with_jubjub`
driven by a counterparty contract's `compose_gated` circuit: the signature
challenge binds to the account's own address through the call boundary
(`kernel.self()` inside the callee names the callee), `auth_nonce` advanced
as on the direct path, and the gate's own counter incremented in the same
transaction. Mixed ZKIR versions proved together (gate v2, account v3). The
corrupted-signature negative was rejected at construction (the in-circuit
assert fires during local execution) with zero state drift on either
contract.

Two consequences follow. First, the account's circuit signatures are now a
public ABI that third-party contracts can compile against, which raises the
cost of the pending erratum fixes (weak-key and revocation) once dependents
exist. Second, a counterparty contract can drive owner-authorised account
operations atomically with its own bookkeeping. That is not yet the
MIP-0007 delegated-owner amendment, which runs the other way: there the
registry is the callee and must recognise the account as its caller, which
is precisely the capability no released line provides.

### 6. Toolchain drift: forwarded arguments must be disclosed

compactc 0.34.0 requires `disclose()` on cross-contract call arguments,
where 0.33.0-rc.2 did not: the compiler formally treats every value
forwarded through a call boundary, signature material included, as
disclosed. That is an honest datapoint for the MIP-0013 privacy claims: what
crosses the seam is public by construction.

### 7. The observer surface is the known linking cost

An indexer observer sees every contract call in the transaction: both
addresses and all entry points (`write_then_read`, `set`, `get`; for P5
`compose_gated`, `rotate_enc_key_with_jubjub`; and for the value probes
`pay_unshielded`, `take_unshielded`, `pay_shielded`, and `take_shielded`),
with the communication commitment value opaque. Cross-contract composition
therefore links the participating contracts exactly as the client-composed
graft did; the MIP-0012 section 6.6 one-hop rules need a call-mode amendment
that prices this linkage rather than a rule that treats it as avoidable.

### 8. Unshielded value moves across the call boundary (P6)

The Payer funded itself by an in-circuit mint of its own color:
`fund_unshielded` minted 1000 to `kernel.self()` (minting to the contract
itself auto-receives, so no claim is needed) and credited the public mirror
in the same circuit. `pay_unshielded(color, 100)` then debited the mirror,
sent 100 unshielded to the Till's contract address, and called
`till.take_unshielded(color, 100)` so the callee claimed the incoming value,
all in one transaction (tx `0074a178af20…`, proving 92 ms, 3545 bytes
proven, first attempt). Both sides moved together: the payer mirror 1000 to
900, `till.unshielded_received` 0 to 100, `till.unshielded_claims` 0 to 1,
and the indexer shows exactly two contract calls under the one hash.

The claim half is load-bearing. Value addressed to a `ContractAddress` is
not credited on its own: a transaction whose contract-addressed output no
recipient circuit claims does not balance, and the ledger rejects it, so a
landed transaction is itself the proof that send and cross-contract claim
paired atomically. The node then attested the settled custody in later
transactions: `assert_unshielded_balance` passed on both contracts (till
100, payer 900), an in-circuit `unshieldedBalance()` assertion the node
would have refused had the mirrors diverged from real ledger custody.

### 9. Shielded value moves too: the issue #658 verdict on the released runtime (P7)

Issue #658 blanked a callee's Zswap local state on the 0.33 line, which made
`receiveShielded` inside a callee toolchain-blocked. On the published
compact-runtime 0.19.0 the verdict is positive: `till.take_shielded`, a
callee, executed `receiveShielded` and claimed the sent coin in the same
transaction as the root's `sendShielded` (tx `0098af566ba1…`, proving
6290 ms, 25974 bytes proven, 24.0 s end to end, first attempt).

The funding and bookkeeping ran the full MIP-0012 section 6.5 pattern:
`fund_shielded` minted a 1000-value coin of the Payer's own color to the
contract itself (the returned nonce equalled the argument nonce), the client
captured `mt_index` 28 from the funding transaction's commitment-tree
window, and the coin entered `pay_shielded` through the `payer_coin`
witness. Every boundary check held:

- the coin the Till holds in its ledger carries the nonce of `result.sent`,
  so the deterministic nonce evolution of `sendShielded` survived the call
  boundary and is verifiable from the callee's public state;
- value (100) and color match the mint, and `shielded_claims` advanced to 1;
- the change coin followed the surviving-coin rule: 900 (1000 funded minus
  100 paid), already a live self-owned output of the Payer, re-captured into
  the coin store with two `mt_index` candidates for the next spend.

One structural consequence deserves emphasis: callees must be witness-free,
so a callee that retains a claimed coin holds it in a public ledger cell
(`QualifiedShieldedCoinInfo` here), nonce, color, and value readable by
anyone. That is exactly what made the nonce check possible in this probe,
and it is also a disclosure cost any value-accepting callee design must
price in.

### 10. A witness-consuming root circuit may hold a call site (P7)

`pay_shielded` consumes the `payer_coin` witness (the wallet-local coin
store) and contains a cross-contract call, and it proved, submitted, and
landed. The witness-free restriction is therefore a callee property only;
the coinless probes had left this open at run time. Passport circuits that
spend witness-held coins can drive counterparty claims directly.

### 11. The fee wall constrains funding, not the mechanism (P6, P7)

Node 2.1.0's fee model mempool-rejects small call+offer transactions
(`OutsideTimeToDismiss`), which is why P0 to P5 stayed coinless. The value
probes isolate the question by funding through in-circuit mints to
`kernel.self()`: no wallet coin offer appears anywhere on either path, and
neither probe contacted the wall (no `OutsideTimeToDismiss` was observed,
and neither the user-funded `deposit_unshielded` fallback nor the BLOCKED
ladder was exercised). The wall therefore remains a documented constraint on
user-funded offers, separate from, and not blocking, the
contract-to-contract value mechanism itself.

### 12. The ledger's Contract arm, observed on real transaction bytes (P8)

The `CallContext.caller` derivation had been a source reading only: no
upstream test builds a context with a caller (`ledger/tests/composable.rs`
uses `QueryContext::new` throughout), and no released Compact can read the
slot it lands in. P8 closes the first half of that gap by running the
ledger's own `ContractCall::context` at tag `ledger-9.1.0.0-rc.3` (commit
`4823b53`), compiled as a small Rust tool (`rust/caller-context/`) against
the git tag and not against any local clone, over the real bytes of the P3
composition captured at four stages: offline-unproven, unproven, proven, and
balanced. On every capture the Tally `set` and `get` frames resolve to
`Contract(<Caller address>)`, selected by the ledger's `find_map` at action
index 0 (the `write_then_read` call whose transcript claims them), and the
root `write_then_read` frame resolves to `None`, because the call-carrying
intent has no unshielded offer and so the `User` arm cannot fire. The
balanced capture is byte-identical to the transaction the indexer holds in
block 963 (tx `0016a72ceb30914e…`, `SucceedEntirely`), so the derivation was
run on the literal on-chain bytes. The Rust and TypeScript views of the same
bytes agree on every address, entry-point hash, communication commitment,
and claim; the one discrepancy surfaced was in the comparison helper, not in
the data (the TypeScript API renders an `Fr` as a tag byte plus the minimal
little-endian value, so a value whose top byte is zero is one byte shorter,
and comparisons must be of values rather than of renderings).

What P8 does not observe is a node handing that value to a contract. Compact
has no reader for context slot 6 and no circuit in this experiment reads it,
so these are the values the ledger computes and marshals into the slot, not
values a callee was seen to receive. The tool never runs `well_formed`, so
it resolves a caller for bytes the node would refuse; a caller value read off
unverified bytes means nothing on its own (see P9's control c).

### 13. Voluntary lending: a chosen-argument claim (P9)

`kernel.claimContractCall(addr, ep_hash, comm)` takes wholly chosen
arguments from Compact source. P9 exports exactly that primitive from a
`Lender` contract (`contracts/lender.compact`, circuit `lend`, whose only
other effect is a counter increment so the transaction changes public
state) and composes, in one intent, a direct root call to `Tally.set(v)`
made by the client and a call to `Lender.lend(tally, ep_hash(set), comm)`
carrying the `set` call's own communication commitment, claimant first. The
composition built offline (no node, no indexer, 26 ms), proved (117 ms),
balanced (301 ms), and landed on node 2.1.0 (tx `006cfacb2b95d931…`,
`SucceedEntirely`, block 1105; `tally.writes` 9 to 10, `lender.lends` 3 to
4). The ledger's own derivation over the landed bytes, which are
byte-identical to the indexer's copy, resolves the `set` call's caller to
`Contract(<Lender>)` and the `lend` call's own caller to `None`. The
identity is lent rather than shared: the ledger names as caller a contract
whose circuit made no call at all, for a root call made by the client.

Three controls fix where the discipline lives. Every one was built, proven
(100 to 126 ms), balanced (288 to 295 ms), and submitted; nothing in the
client, the prover, or the wallet refused any of them, and the wasm binding
accepted every graft, so whatever `construct.rs:1049-1076` does in Rust,
the binding this path uses did not refuse these compositions. The node
refused all three at admission, and its own log names the check while
quoting the SHA-256 of the submitted bytes, which equals the recorded hash
of each captured arm (`evidence/p9-node-rejections.txt`):

| Control | Composition | Node refusal |
|---------|-------------|--------------|
| a (subset) | the genuine composition with the claimed commitment plus one | `Malformed(EffectsCheck(RealCallsSubsetCheckFailure))` |
| b (uniqueness) | `[lend, write_then_read, set, get]`: the genuine `set` sub-call of `Caller` also claimed by `Lender` | `Malformed(EffectsCheck(ClaimedCallsUniquenessFailure))` |
| c (sequencing) | `[set, lend]`: the claimant placed after the claimed call | `Malformed(SequencingCheck(CallSequencingViolation))` |

The wallet SDK surfaced each as a bare `SubmissionError`, and the RPC layer
as Substrate `InvalidTransaction::Custom` codes 212, 216, and 219; the
numbering is the node's and is part of no interface we rely on, and the
names above come from the node's log, tied to each arm by hash. The
outcomes were stable across three independent full runs. The evidence
JSON's own `errorCodeMapping` paragraph, written by the probe before the
node log was read, records the mapping as not established; the log capture
supersedes it.

Two further facts come out of the derivation over the control bytes. In
control a the claim matches no call, so the `Contract` arm does not fire
and `set` resolves to `None`. In control b the `set` call carries two
claims and the derivation, taken alone, picks the earlier action, the
`Lender`, over the `Caller` whose circuit genuinely made the call; those
bytes never entered a block, so the supersession is a property of the
derivation in isolation, never realised on chain, and on the checks we
exercised the `Contract` arm is lendable but not overridable.

What P9 does not observe: a contract that exports no claim circuit being
made to emit one. The claim is an effect of the `Lender`'s own transcript
and reaches the first public input of its proof, so on the same reasoning
such a contract should not be forgeable into lending, but that converse was
not probed. Nor, as in P8, did any circuit read slot 6.

## Take-aways the Passport programme must carry forward

Four consequences of this evidence are easy to lose in the probe detail and
must survive into any pull request, MIP amendment, or adoption discussion:

1. **Atomicity is the headline gain.** The whole call tree commits or fails
   as one transaction, enforced by the node (P4). Composed operations across
   contracts need no client-side pairing discipline and can never half
   complete. This is the property that makes contractual composition safer
   than the client-composed graft it replaces.
2. **A callee cannot identify its caller, and the gap is in the language.**
   The ledger derives the calling contract's address per call frame and
   places it at VM context slot 6; we have watched the ledger's own code do
   so on our transaction bytes (P8). Compact has no reader for that slot,
   and no layer anywhere records which circuit of the caller invoked the
   callee. On every released line, therefore, no contract can grant
   authority because the passport account (or any specific contract) called
   it; authority must travel in the arguments, as the account's signature
   seam already does. Any design that keys access on the calling contract is
   unimplementable until upstream surfaces the slot, and any design that
   keys it on the calling circuit needs a protocol change as well. And when
   the slot is surfaced, its value means "the contract whose transcript
   claims this call", not "the contract whose circuit called me": a contract
   exporting a chosen-argument claim can lend that identity to a root call
   the client made, and the node admits it (P9). A callee-side policy keyed
   on the slot is therefore a policy about which contract consented to be
   named, and a specification of the reader must say so.
3. **Becoming a callee makes the account's circuits a public ABI.** Third
   party contracts compile against exact circuit signatures and deployed
   verifier keys, so every dependent breaks when a signature changes. The
   pending weak-key and revocation erratum fixes should land before the
   ecosystem is invited to compose against the account contract, not after.
4. **Composed value transfer is send plus same-transaction claim.** Value
   addressed to a contract is not credited on its own: the ledger rejects a
   transaction whose contract-addressed output no recipient circuit claims,
   so a paying circuit must drive a claim circuit on the payee in the same
   transaction (P6, P7). Every value-accepting Passport contract therefore
   needs exported claim circuits, which join its public ABI; and because
   callees must be witness-free, a callee that retains a claimed shielded
   coin holds it in public ledger state, a disclosure cost that must be
   priced into any custody design that composes payments.

## What this does not show

- **User-funded value across a call boundary.** Both value probes fund by
  in-circuit mint of the payer's own color, precisely so that node 2.1.0's
  fee wall (mempool rejection of small call+offer transactions,
  `OutsideTimeToDismiss`) cannot confound the mechanism question. The wall
  was never contacted, so whether a wallet-funded deposit paired with a
  composed payment clears it remains untested; and nothing here prices real
  Night or Dust flows, because the moved tokens are probe-minted colors.
- **A send without a claim.** The claim requirement (value addressed to a
  contract must be claimed by a recipient circuit in the same transaction,
  or the ledger rejects the transaction) is documented ledger behaviour the
  contracts are designed around; no probe submitted the failing control.
  Likewise `take_shielded` claimed exactly one coin, so its
  `mergeCoinImmediate` branch for a second incoming coin never executed.
- **Reading the caller from inside a callee.** No circuit of ours reads
  context slot 6, because the language has no reader for it: `kernel` has
  sixteen members on compactc 0.34.0 and `caller` is not among them
  (`operation caller undefined for ledger field type Kernel`). A node
  evaluating such a read therefore remains unobserved. The derivation
  itself is no longer a source reading only: P8 ran the ledger's own
  `ContractCall::context` at `ledger-9.1.0.0-rc.3`, built from the git tag,
  over our transaction bytes, including the bytes that landed in block 963,
  and watched it take the calling contract's address from whichever other
  call in the same intent claims this call and fall to `None` where no
  claim and no unshielded input exists; the `User` arm was never exercised,
  because every call-carrying intent here was coinless. The claim
  discipline was observed on the node, to this extent: P9's three controls
  were refused at admission by name (subset, uniqueness, and sequencing),
  while its main arm, a chosen-argument claim on a root call the claimant
  never made, was admitted. What stays missing is the Compact surface on
  the slot and, separately and more deeply, any record anywhere of the
  calling circuit: the claimed-call record carries the callee's entry-point
  hash, never the caller's. P5 works regardless, because the account's seam
  authenticates the owner's signature, not the caller: any counterparty
  contract holding a valid owner-signed bundle can drive the call.
- **Forging a claim into a non-consenting contract.** P9 shows that a
  contract exporting a claim circuit can lend its identity; no arm attempted
  to attach a claim to a contract whose circuits emit none, so the
  unforgeability of the `Contract` arm against a third party rests on the
  source reading (the claim is a transcript effect bound into the first
  public input of the claimant's proof), not on a refused transaction.
- **Dynamic implementation binding.** Draft CoIP-3; the shipped model
  resolves one implementation per declared contract type statically at
  compile time, and no probe exercises substituting a callee implementation.
- **The 0.33.0-rc line.** Superseded by the 0.34.0 pin and not tested here;
  this evidence certifies nothing about it.
- **A public network.** Ledger 9 is a fresh-chain release-candidate stack
  with no 8-to-9 state migration; every result here comes from a localnet
  built from rc images. No public Midnight network runs this ledger yet, so
  this is pre-deployment evidence, not observed production behaviour.
