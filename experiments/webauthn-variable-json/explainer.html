01

From an assertion to a verified state update

The expensive work happens on the proving side. The ledger verifies a compact proof of that work; it does not run the witness’s JavaScript JSON parser.

WITNESS = COMPUTATION HELPER

“Here is my proposed answer.”

  • Parses the JSON outside the proof.
  • Suggests the origin, origin length and prefix length.
  • Supplies bits and carries for SHA-256 arithmetic.

A malicious prover can replace this code. An honest JSON.parse call alone gives no on-chain guarantee.

CIRCUIT = ENFORCED RELATION

“Those answers must fit these bytes.”

  • Binds the expected challenge and enrolled key / RP / origin.
  • Checks lengths, field boundaries, UP+UV flags and buffer tail.
  • Computes the signed hash and verifies the P-256 signature.

A false answer that violates these constraints cannot support a valid proof.

clientHash = SHA-256(clientDataJSON[0 : length])
signedDigest = SHA-256(authenticatorData || clientHash)
require P-256.verify(signedDigest, signature, enrolledPublicKey)

The second hash has a fixed 69-byte input: 37 bytes of authenticator data + a 32-byte client hash. The first hash is the new variable-length part. Proving inputs are available to the prover / proof server; the JSON and its length are not disclosed as ledger fields by this probe.

02

A fixed container, a variable message

The circuit always receives a 256-byte buffer. A separate length tells it which bytes belong to the signed message. Unused capacity must contain zeros, but those zeros are not part of the message hash.

140 message bytes + 52 SHA-padding bytes occupy 3 blocks. The circuit selects the digest after block 3.

All five blocks are still evaluated. The fixed circuit accommodates the worst case. A shorter message selects an earlier state; it does not shrink this circuit or remove the later computations.

SHA padding is different from the zero-filled input capacity. It adds 0x80, zeros and an 8-byte bit-length field. Blocks needed = ceil((L + 9) / 64). At 248 bytes, the padding requires a fifth block.

Why a fake length fails: shortening the input can violate field or zero-tail checks. Extending it changes the hash. With the original assertion signature, that changed message fails signature verification.
03

“Variable-length” does not mean “any JSON.”

Both modes enforce the required WebAuthn prefix, challenge, enrolled origin and crossOrigin:false. Their difference is what may follow those fields. The constructor pins the mode.

Compare circuit rules

{"type":"webauthn.get","challenge":"AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8","origin":"https://wallet.example.test","crossOrigin":false}

✓Permitted shape · strict mode · 140 bytes

Strict mode constrains the complete four-field serialization, including its closing brace. The origin may vary in length but must match enrolled policy.

This is a rule illustration, not a prover running in your browser. Results assume the appropriate signature over these exact bytes, matching enrolled key / RP policy and valid authenticator flags. Examples fit within 256 bytes.

Strict: the whole supported envelope

Exactly the four fields, in order, with the required byte formatting. Origin length can vary from 1–96 bytes. Extra fields and whitespace changes are rejected.

Limited: required prefix + signed remainder

Uses WebAuthn’s standard limited-verification approach for same-origin assertions. Requires } or , next. Hashes the full remainder, without proving its arbitrary JSON syntax.

The deliberate boundary: a forged witness can bypass its own JSON.parse. In limited mode, a correctly signed malformed suffix can still satisfy the circuit. It cannot bypass the required prefix, policy binding or signature checks. Strict mode rejects that suffix.
04

What actually changes in this contract?

This is a verification probe. Its constructor pins the challenge, policy and mode. A successful verify_webauthn call proposes writing the client-data hash into accepted.

expected_challenge : Bytes<32>Public constructor-pinned expectation; encoded to 43 base64url characters for comparison.
enrolled_policy : Bytes<32>Public commitment binding the private RP hash, origin buffer, origin length and P-256 key.
limited_verification : BooleanPublic mode choice, fixed by the constructor for this instance.
accepted : Bytes<32>Public diagnostic client hash written by a successful call. Initially zero.
Read accepted as a diagnostic, not an authorization badge. The separate hash_bytes benchmark can write it too. This experiment does not spend funds, issue grants or implement replay protection. Those require integration with the account’s actual operation challenges and authorization rules.

SHA-256 adds words modulo 2³². We removed redundant intermediate decompositions and used cheaper conditional bit operations, while retaining the arithmetic constraints. That improved the initial experiment, crossing a power-of-two proving-domain threshold. It did not produce a size or cost win over the previous fixed-profile verifier.

The previous fixed verifier recorded about 12 seconds on repeat proof requests. The new values above are one sample each, including ~1.91 GB of streamed key material, decoding and proving. The first run fetched public parameters and overlapped other tests. This is not a controlled timing comparison or evidence that longer JSON proves faster. Deployment budget: the WebAuthn verifier key is 2,745 bytes. With the separate hash benchmark key, this probe totals 4,098 verifier bytes—within the 15,000-byte wave budget. The large prover key stays on the proving side. A combined account deployment still needs its own budget.
06

Correctness passed. The size objective failed.

A working construction can still be a negative engineering result. Its bounded input flexibility is demonstrated; smaller proofs, smaller verifier keys and better proving efficiency are not.

Completed correctness evidence

  • ✓
    Hash matches Node/OpenSSL at every length 0–256

    Includes padding boundaries, zero inputs and dishonest arithmetic advice.

  • ✓
    14/14 compiled execution groups pass

    Variable origins, signature and policy failures, extra fields, and the limited-mode syntax boundary.

  • ✓
    Five raw witness mutations fail ZKIR assertions

    Bit, carry, origin, prefix length and input length. Generated JavaScript checks are bypassed.

  • ✓
    Two real proofs verified and applied locally

    140-byte strict and 256-byte limited assertions, software ES256, same verifier key.

How to interpret that

We have demonstrated bounded variable-length verification. We have not demonstrated an unrestricted JSON parser or unlimited input length. Correctness PASS does not overturn the negative size/cost result.

The existing real Safari assertion was replayed in execution and ZKIR checks. New lengths in the proof tests came from a software signer, not fresh browser/passkey interactions.

The proof tests used an in-memory ledger with fee balancing disabled. Node acceptance, nonce/replay handling and device/grant integration are outside this experiment. The result does not recommend promoting this probe into the account.
