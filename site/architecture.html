Notes for reviewers

  • This is a context + container view. It shows where components live and who they talk to, not the data flow for any specific operation. The How it works page walks the account lifecycle end to end.
  • How authority flows. The user authorises with a biometric on a device-bound passkey; the derived device key signs each call with JubJub Schnorr (C5, C9). Witnesses never leave the device — proving happens in-tab (C6, C7) — and the account custody contract verifies the proof in-circuit and is the sole authority over the account's assets (C1, C4). Recovery guardians reach the account only through the epoch-bump seam (C14, C15); the name binds to the account through the upstream registry (C2), and the DID linkage is a live C3 question.
  • Workstreams are explicitly unresolved. C3 (DID surface), C22 (intent surface), C24 (fee model — mechanism confirmed, sponsor operator open), and C25 (cross-chain interface) are dashed because a live decision remains. C4 (asset custody) has resolved to stateless contract custody, normative in MIP-0012. Placement may shift once a workstream resolves.
  • C3 sits inside the on-chain zone as the primary architectural element, but the workstream's resolution runs through engagement with the external midnight-did repository — drawn alongside in the external identity ecosystem.
  • C8 (domain separation) is cross-cutting and shown as an annotation rather than placed in any single zone — every persistentHash use site needs a registered prefix.
  • C6 / C7 / C20 are placed in the proof server sub-zone for clarity; in practice their orchestration code lives in the wallet runtime. The trust property is what matters: witnesses must not leave the user device.
  • C26 (AI agent skills) is omitted — it is a meta-deliverable about documentation and tooling, not a runtime element.
  • The MVP vs. v1.0 split is not represented here; this view holds for both readings. Standards and Demo document where they diverge.
